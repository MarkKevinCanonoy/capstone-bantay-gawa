1. INTRODUCTION
1.1. Purpose
This Software Requirements Specification (SRS) document specifically describes the
BantayGawaMobile system - an intelligent mobile workforce attendance verification system
that serves the users from the Environment and Natural Resources Office (ENRO) of Ormoc
City City Hall by addressing the problem of time theft and unverified work done among field
workers through location based attendance validation using geofencing with real-time facial
recognition.

1.2. Scope
BantayGawaMobile is a mobile-first workforce management platform for LGU field workers
that only allows them to log attendance if they are physically within the work zones. The
system covers:
●​ User Authentication: Multi-factor authentication with QR Code first-time login,
session storage, face recognition.
●​ Role-Based Access Control: 3 distinct roles with role-specific permissions
●​ Geofence Management: Circular, Polygon geofences.
●​ Attendance Management: Time-in, Break-in, Break-out, Time-out with face, geofence
validation.
●​ Field Accomplishment Reporting: Work completion proof submission with geotagged
images.
●​ Leave Request Management: Submit, view, approve/deny leave requests
●​ Performance Credit System: Star-based worker performance with automated alerts.
●​ GIS Workforce Map: Real-time worker locator, Work zone status.
●​ Offline Capability: Attendance, proof capture without internet with auto-sync
●​ Notification System: In-app messages for announcements, alerts, updates.
●​ Report Generation: Daily, weekly, monthly report PDF/Excel export.
The system is built using Flutter, Supabase with PostGIS, MobileFaceNet with CNN
antispoofing, flutter_map with OpenStreetMap, Firebase Cloud Messaging, hosted on Vercel.
System does not integrate with existing LGU payroll & HR as per current scope.

BantayGawaMobile is a standalone system that operates independently. The system consists
of:
1.​ Mobile Application (Flutter): For Field Workers (primary) and Field Supervisors
(limited access)
2.​ Web Dashboard (Flutter Web): For Admin and Field Supervisor full management
access
3.​ Backend Services: Supabase (authentication, database, real-time) + PostGIS (spatial
data)
4.​ Facial Recognition Engine: MobileFaceNet + CNN Anti-Spoofing (on-device,
offline)
5.​ GIS/Mapping Service: flutter_map + OpenStreetMap
6.​ Notification Service: Firebase Cloud Messaging (in-app push notifications)
7.​ Local Storage: SQLite (offline data caching and sync)

2.4. Operating Environment
●​ The system shall run in android 7+ and IOS 10+ capable of using camera, GPS,
Internet, SQLite for offline storage.
●​ The system shall be accessible through any modern web browser (Google Chrome,
Microsoft Edge, Mozilla Firefox, Safari) on desktop or laptop computer.
●​ The system shall use Supabase for database storage.
●​ The system shall use Vercel (free tier) for web hosting.
●​ The system shall use Firebase Cloud Messaging for push notification features,
●​ The system shall use OpenStreetMap for in-app navigation feature for geofencing.

2.5. Design Constraints
●​ The system must utilize open-source and free-tier solutions (e.g., Supabase Free Tier
and Vercel Free Tier).
●​ The system must comply with the Data Privacy Act of 2012 (Republic Act No.
10173).
●​ Core field functions, including attendance recording and proof capture, must remain
operational even without an internet connection.
●​ The mobile application must support Android 7.0 and above. Older devices may have
limited face recognition capabilities.
●​ Facial recognition data must be stored locally on the device and not in cloud storage.
●​ The system must be deployable using minimal LGU IT infrastructure requirements.
●​ The system must support English and Filipino, with Cebuano and Waray considered
as a future enhancement.

●​ The geofencing feature must support polygon-shaped boundaries to accommodate
irregular work area boundaries.
●​ All proof images must include embedded date, time, and location information as both
image metadata and a visible overlay.

2.6. Assumptions
●​ Field workers have access to Android 7.0 or later smartphones equipped with a
camera and GPS.
●​ Field workers possess sufficient digital literacy to operate the mobile application.
●​ Internet connectivity may be intermittent, and offline functionality is sufficient to
support field operations during connectivity gaps.
●​ GPS signals are available in all designated work areas to enable geofence validation.
●​ The LGU has designated administrative personnel to manage and maintain the
system.
●​ The LGU has assigned Field Supervisors to monitor workers in their designated work
areas.
●​ Workers are willing to use facial recognition and location tracking for attendance
verification.
●​ The LGU provides complete and accurate worker information during the initial
system setup.
●​ The LGU complies with the Data Privacy Act of 2012 (Republic Act No. 10173) and
other applicable data protection regulations.
●​ The Supabase Free Tier is sufficient to support the initial deployment, including
approximately 100 workers and 5 supervisors.
●​ The Vercel Free Tier is sufficient to host the web dashboard during the initial
deployment.
●​ Firebase Cloud Messaging (FCM) services are available and accessible in the
Philippines.
●​ OpenStreetMap map tiles are available for geographic visualization.
●​ Pre-trained MobileFaceNet and CNN Anti-Spoofing models are available and can be
deployed on supported Android devices.
●​ Payroll integration is not required during the initial deployment of the system.
●​ Users can understand English and/or Filipino for application navigation.

●​ Worker devices have cameras capable of capturing facial images with sufficient
quality for recognition.
●​ The LGU can facilitate worker enrollment, including face registration and QR code
distribution, during onboarding.

2.7. Dependencies
●​ The system depends on Supabase for user authentication, database management, and
real-time services.
●​ Spatial data processing depends on the PostGIS extension in PostgreSQL.
●​ Push notifications depend on the availability of Firebase Cloud Messaging (FCM).
●​ Map visualization depends on the availability of OpenStreetMap tile servers.
●​ The web dashboard depends on Vercel hosting services.
●​ Real-time synchronization and online features depend on internet connectivity.
●​ Geofence validation depends on the availability and accuracy of GPS signals.
●​ The mobile application depends on devices running Android 7.0 or later.
●​ Face recognition functionality depends on the TensorFlow Lite runtime.
●​ Attendance verification depends on workers completing the face registration process.
●​ Successful deployment depends on the cooperation and adoption of the system by
LGU personnel.
●​ Initial system setup depends on the successful migration of worker data.
●​ System deployment depends on LGU approval of privacy policies and related
documentation.
●​ Effective system adoption depends on the successful completion of user training.
●​ Future use of paid cloud services depends on LGU budget approval.
●​ Certain system functions depend on the availability and reliability of third-party
services and APIs.

3. USE CASE DEVELOPMENT
3.1. UC-01 - Create User Account
Actor: Admin
Goal: To create a new user account for a Field Worker or Field Supervisor and register their
facial data for biometric verification.
Precondition: The Admin is logged in with valid credentials and has the necessary
permissions to create user accounts.
Main Flow:
1.​ The Admin navigates to Employee Management page.
2.​ The Admin selects "Add Employee".
3.​ The Admin enters employee details (Name, Role, Contact Information).
4.​ The Admin selects the employee's role (Field Worker or Field Supervisor).
5.​ The Admin uploads or uses the system camera to capture the employee's face.
6.​ The system converts the captured face into a face embedding (feature vector) .
7.​ The system securely stores the face embedding in the database .
8.​ The system automatically generates a unique QR code for the employee.
9.​ The Admin assigns the employee to a work area (if applicable).
10.​ The Admin saves the account.
11.​The system creates the account and sends a welcome notification.
Alternative Flow:
1.​ If the Admin submits incomplete information, the system prevents submission and
highlights all required fields.
2.​ If face capture fails, the system allows the Admin to retry.
Postcondition: The user account is created in the system; the QR code is generated and
available for printing; the face embedding is stored securely for future biometric verification.

3.2. UC-02 - Manage Work Areas and Geofences
Actor: Admin
Goal: To create, edit, or delete work areas with defined geofence boundaries (polygon or
circle) for attendance restriction
Precondition: The Admin is logged in and has access to the Area Management module
Main Flow:

1.​ The Admin navigates to Area Management page.
2.​ The Admin views the interactive map with existing geofences.
3.​ The Admin selects "Add Area".
4.​ The Admin draws a geofence on the map (polygon or circle).
5.​ The Admin sets the area name and other properties.
6.​ The Admin assigns a Field Supervisor to the area.
7.​ The Admin assigns Field Workers to the area.
8.​ The Admin saves the changes.
9.​ The system creates the geofence and assigns the workers and supervisor.
Alternative Flow:
1.​ If the Admin draws an invalid geofence (self-intersecting polygon), the system
prevents creation and prompts the Admin to redraw.
2.​ If the Admin attempts to delete an area with active workers assigned, the system
warns and requires confirmation before proceeding.
3.​ If the Admin edits an existing geofence, the system updates the boundary and notifies
all assigned workers.
Postcondition: The work area with geofence is created/updated/deleted in the system. The
assigned workers can now log attendance only within this boundary.

3.3. UC-03 - Approve or Deny Leave Request
Actor: Field Supervisor
Goal: To review, approve, or deny a leave request submitted by a Field Worker
Precondition: The Admin is logged in. A leave request has been submitted by a Field
Worker
Main Flow:
1.​ The Admin navigates to Leave Management page.
2.​ The Admin views the list of pending leave requests (filtered by area).
3.​ The Admin selects a leave request.
4.​ The Admin reviews the worker's details, reason for leave, and optional proof image.
5.​ The Admin selects "Approve" or "Deny".
6.​ If denying, the Admin enters a reason for denial.
7.​ The system updates the leave request status.
8.​ The system sends a notification to the worker and their Field Supervisor.
Alternative Flow:

1.​ If the Admin denies the request without providing a reason, the system prompts the
Admin to enter a reason.
Postcondition: The leave request is approved or denied; the worker and Supervisor are
notified of the decision

3.4. UC-04 - Review and Approve Accomplishment Proof
Actor: Field Supervisor
Goal: To review, approve, or deny an accomplishment proof submitted by a Field Worker.
Precondition: The user is logged in, an accomplishment proof has been submitted by a Field
Worker. For the Field Supervisor, the proof must be from an assigned area.
The user is logged in; an accomplishment proof has been submitted by a Field Worker; for
Field Supervisor, the proof must be from an assigned area.
Main Flow:
1.​ The user navigates to Accomplishment Management page.
2.​ The user views the list of pending proofs (filtered by area for Supervisor; all areas for
Admin).
3.​ The user selects a proof.
4.​ The system displays the proof image with visual timestamp and coordinates overlay.
5.​ The system displays the extracted metadata summary (date, time, location).
6.​ The system indicates if the metadata matches the assigned area.
7.​ The user selects "Approve" or "Deny".
8.​ If denying, the user enters a reason.
9.​ The system updates the proof status.
10.​The system sends a notification to the worker and the other approver (Supervisor or
Admin).
Alternative Flow:
1.​ If the user is Field Supervisor and the field worker who submits is not from their
assigned area, the system does not display the accomplishment report.
2.​ If the metadata extracted from the image does not match the assigned area, the system
flags this and displays a warning to the user.
3.​ If the other approver has already approved the proof, the current user can request an
appeal.
Postcondition: The accomplishment proof is approved or denied; the worker and other
approver are notified.

3.5. UC-05 - Generate Reports
Actor: Admin or Field Supervisor
Goal: To generate and export attendance or performance reports.
Precondition: The user is logged in.
Main Flow:
1.​ The user navigates to Reports page.
2.​ The user selects a report type (Attendance Summary, Area Performance, Worker
Performance, Accomplishment Report).
3.​ The user applies filters (date range, area, worker, status).
4.​ The system displays a preview of the report.
5.​ The user selects export format (Excel, PDF, or CSV) 6. The system generates and
downloads the report
Alternative Flow:
1.​ If the user is a Field Supervisor, the system only shows areas assigned to them.
2.​ If no data matches the selected filters, the system displays a "No data found" message.
Postcondition: The report is generated and downloaded in the selected format.

3.6. UC-06 - Send Notification
Actor: Admin
Goal: To send in-app notifications to users for announcements, warnings, or confidential
feedback.
Precondition: The Admin is logged in.
Main Flow:
1.​ The Admin navigates to Notifications page.
2.​ The Admin composes a message.
3.​ The Admin selects recipients (All Users, All Supervisors, All Workers, Specific
User).
4.​ The Admin marks the notification as "Confidential" if needed (only recipient sees).
5.​ The Admin sends the notification.
6.​ The system delivers the in-app notification to selected recipients via Firebase Cloud
Messaging.
Alternative Flow:
1.​ If the Admin selects "Confidential" for a notification, the system ensures only the
intended recipient can view it.

2.​ If the Admin sends a notification without a message, the system prevents sending.
Postcondition: The notification is sent to all selected recipients.

3.7. UC-07 - Shuffle Worker Assignments
Actor: Admin
Goal: To reassign Field Workers to different work areas, typically done monthly.
Precondition: The Admin is logged in; the monthly shuffle is due.
Main Flow:
1.​ The Admin navigates to Area Management page.
2.​ The Admin views all work areas with current worker assignments.
3.​ The Admin selects a work area.
4.​ The Admin views the list of available workers.
5.​ The Admin selects workers to assign to this area.
6.​ The Admin confirms the assignment.
7.​ The system updates the worker assignments.
8.​ The system sends notifications to affected workers.
Alternative Flow:
1.​ If the Admin attempts to assign a worker who is already assigned to another area, the
system warns and prompts confirmation.
2.​ If the Admin selects "Bulk Assign," the system allows assigning multiple workers to
multiple areas simultaneously.
Postcondition: Worker assignments are updated; affected workers receive notifications of
their new assignments.

3.8. UC-08 - View GIS Workforce Map
Actor: Admin or Field Supervisor
Goal: To view real-time worker locations and work zone status on an interactive map.
Precondition: The user is logged in.
Main Flow:
1.​ The user navigates to GIS Map page.
2.​ The system displays an interactive map with: - Worker markers showing real-time
locations - Color-coded attendance status (On-site/Off-site) - Geofence overlays for
all or assigned areas - Area names and boundaries.
3.​ The user clicks on a worker marker.

4.​ The system displays worker details (name, area, status, last check-in).
Alternative Flow:
1.​ If the user is a Field Supervisor, the system only displays areas assigned to them.
2.​ If the user enables "Historical Movement" toggle, the system displays worker
movement paths for the day.
Postcondition: The user has real-time visibility of worker locations and zone status.

3.9. UC-09 - View and Respond to Alerts
Actor: Admin
Goal: To view and respond to system-generated alerts for consecutive absences, credit
warnings, and breaches.
Precondition: The Admin is logged in; alerts have been generated by the system.
Main Flow:
1.​ The Admin navigates to Notifications/Alerts page.
2.​ The Admin views alerts categorized by type: - Consecutive Absence Alerts (3+
absences) - Credit Score Warnings (Yellow/Red) - Breach Alerts.
3.​ The Admin selects an alert.
4.​ The system displays affected worker details.
5.​ The Admin sends a warning notification to the worker and Supervisor.
6.​ The system logs the alert response.
Alternative Flow:
1.​ If the Admin dismisses an alert without action, the system logs the dismissal for audit
purposes.
Postcondition: The alert is acknowledged and responded to; the response is logged in the
system.

3.10. UC-10 - Monitor Assigned Workers (Field Supervisor)
Actor: Field Supervisor
Goal: To monitor the attendance and location status of Field Workers assigned to the
Supervisor's areas
Precondition: The Field Supervisor is logged in.
Main Flow:
1.​ The Supervisor navigates to the Dashboard.
2.​ The Supervisor views the list of assigned areas.

3.​ The Supervisor views the team attendance summary.
4.​ The Supervisor views the GIS map showing worker locations in assigned areas.
5.​ The Supervisor clicks on a worker marker.
6.​ The System displays the worker's profile with attendance history
Alternative Flow:
1.​ If the Supervisor filters workers by area, the system displays only workers in that area
Postcondition: The Supervisor has full visibility of all assigned workers' attendance and
location status.

3.11. UC-11 - Report Worker Issue
Actor: Field Supervisor or Field Worker
Goal: To report an issue about another worker's conduct, absence, or performance to the
appropriate authority.
Precondition: The user is logged in, and an issue has been observed.
Main Flow:
1.​ The user navigates to the Report Worker page.
2.​ The user selects the worker to report
3.​ The user selects an issue type (e.g., not working, outside assigned area, poor
performance).
4.​ The user adds a description of the issue.
5.​ The user optionally attaches a proof image.
6.​ The user submits the report.
7.​ The system sends a notification to the Supervisor (if Worker reports) or Admin (if
Supervisor reports).
Alternative Flow:
1.​ If the user submits a report without a description, the system prevents submission and
prompts for a description.
Postcondition: The report is sent to the appropriate authority for review.

3.12. UC-12 - Generate Reports (Supervisor)
Actor: Field Supervisor
Goal: To generate and export reports specific to the Supervisor's assigned areas.
Precondition: The Field Supervisor is logged in.
Main Flow:

1.​ The Supervisor navigates to Reports page.
2.​ The Supervisor selects a report type (Attendance Summary, Area Performance).
3.​ The Supervisor applies filters (date range, area, worker).
4.​ The system displays a preview of the report.
5.​ The Supervisor selects export format (Excel, PDF, or CSV).
6.​ The Supervisor optionally sends the report to Admin.
7.​ The system generates and downloads/sends the report.
Alternative Flow:
1.​ If the Supervisor attempts to generate a report for an unassigned area, the system does
not show that area.
Postcondition: The report is generated and exported or sent to Admin.

3.13. UC-13 - View Leave Requests (Supervisor)
Actor: Field Supervisor
Goal: To view leave requests submitted by workers assigned to the Supervisor's areas.
Precondition: The Supervisor is logged in.
Main Flow:
1.​ The Supervisor navigates to Leave Management page.
2.​ The Supervisor views the list of leave requests from assigned workers.
3.​ The Supervisor selects a request to view details.
4.​ The system displays the request details (worker name, reason, dates, proof image).
5.​ The Supervisor notes they cannot accept/deny (Admin only).
6.​ The Supervisor optionally adds comments for Admin's consideration
Alternative Flow:
1.​ If the Supervisor filters leave requests by status, the system displays only requests
matching the filter.
Postcondition: The Supervisor is informed of all leave requests from assigned workers.

3.14. UC-14 - First-Time Login via QR Code
Actor: Field Worker
Goal: To log in to the system for the first time by scanning the QR code printed on the
worker's ID card.

Precondition: The Admin has created the worker's account and face embedding; the QR
code is printed on the worker's ID card or available digitally.
Main Flow:
1.​ The worker downloads the mobile application.
2.​ The worker opens the app and sees the "Scan ID to Login" button.
3.​ The worker taps the button.
4.​ The app opens the camera.
5.​ The worker scans the QR code on the ID card.
6.​ The app authenticates the worker.
7.​ The system stores the session persistently.
8.​ The worker is logged in and sees the Dashboard
Alternative Flow:
1.​ If the worker scans an invalid QR code, the system displays an error and prompts the
worker to try again.
2.​ If the worker has saved the QR code as an image, they can choose to scan from the
gallery.
Postcondition: The worker is logged in; the session is saved for all future use.

3.15. UC-15 - Log Attendance
Actor: Field Worker
Goal: To log attendance (Time-in, Time-out) using facial recognition and geofence
validation.
Precondition: The worker is logged in; the worker is within the assigned geofence boundary.
Main Flow:
1.​ The worker opens the app (auto-logged in).
2.​ The worker navigates to the Attendance page.
3.​ The worker selects an attendance action: - Time-in - Time-out.
4.​ The system checks if the worker is inside the assigned geofence.
5.​ The system performs facial recognition (on-device).
6.​ The system verifies the captured face matches the registered face embedding.
7.​ If both checks pass, the system logs attendance with: - Timestamp - GPS coordinates Selfie proof.
8.​ The system updates the attendance status on the dashboard.

Alternative Flow:
1.​ If the worker is outside the assigned geofence, the system displays "Outside
geofence" and does not allow attendance logging.
2.​ If facial recognition fails, the system uses the built-in camera to capture a selfie with
embedded date, time, and location.
3.​ If there is no internet connection, the system caches the attendance locally and syncs
when connectivity is restored.
Postcondition: Attendance is recorded (or cached for offline sync) in the system.

3.16. UC-16 - Submit Accomplishment Proof
Actor: Field Worker
Goal: To submit proof of completed work via image capture with embedded location, date,
and time metadata.
Precondition: The worker is logged in, and work has been completed.
Main Flow:
1.​ The worker navigates to the Accomplishment page.
2.​ The worker taps "Upload Today's Report" (default assigned area).
3.​ The worker opens the app's built-in camera.
4.​ The worker captures a proof image.
5.​ The system automatically: - Embeds date, time, and location coordinates in metadata Burns visual overlay on the image (date, time, coordinates).
6.​ The worker adds an optional message.
7.​ The worker submits the proof.
8.​ The system validates the metadata against the assigned area.
9.​ The system sets the status to "Pending".
10.​The system notifies the Supervisor and Admin.
Alternative Flow:
1.​ If the worker taps the floating "+" button, the worker selects an area from the map
(assigned or unassigned) before capturing.
2.​ If the captured image does not contain valid metadata, the system warns the worker
and allows recapture.
3.​ If there is no internet, the proof is cached locally and syncs when online.

Postcondition: The accomplishment proof is submitted and pending Supervisor/Admin
approval.

3.17. UC-17 - Request Leave
Actor: Field Worker
Goal: To submit a leave request with a reason and optional proof image.
Precondition: The worker is logged in.
Main Flow:
1.​ The worker navigates to the Leave page.
2.​ The worker selects a leave type (Emergency, Sick, Vacation, Other).
3.​ The worker enters start date, end date, and reason (required).
4.​ The worker optionally attaches a proof image.
5.​ The worker submits the request.
6.​ The system sends a notification to the Supervisor (informed) and Admin (for
approval).
7.​ The request status shows "Pending".
Alternative Flow:
1.​ If the worker submits a request without a reason, the system prevents submission and
prompts for a reason.
Postcondition: The leave request is submitted and awaiting Admin approval.

3.18. UC-18 - View Performance Credits
Actor: Field Worker
Goal: To view personal performance credit score, color indicator, and credit history.
Precondition: The worker is logged in.
Main Flow:
1.​ The worker navigates to the Profile page.
2.​ The system displays the worker's star credit score (0-100) with color indicator: 80-100: Green (Good) - 50-70: Yellow (Warning) - 10-40: Red (Critical).
3.​ The worker views the credit history: - Dates of deductions (absences) - Dates of
additions (attendance, approved reports).
4.​ The worker views the attendance summary.
Alternative Flow:
1.​ If the credit score is Yellow (50-70), the system displays a warning message.

2.​ If the credit score is Red (10-40), the system displays a critical alert.
Postcondition: The worker can see their current performance status and history.

3.19. UC-19 - Offline Attendance Capture
Actor: Field Worker (System)
Goal: To log attendance when there is no internet connectivity.
Precondition: The worker has no internet connectivity; the worker is within the geofence.
Main Flow:
1.​ The worker opens the app (offline mode indicator shown).
2.​ The worker performs an attendance action.
3.​ The system captures a selfie with embedded metadata.
4.​ The system caches the attendance data locally (SQLite).
5.​ The system displays "Offline - Will sync when online" message.
6.​ When internet is restored, the system auto-syncs the cached data.
7.​ The system validates the metadata against the assigned area.
Alternative Flow:
1.​ If the worker attempts to submit multiple offline records without syncing, the system
queues them in order of creation.
Postcondition: Attendance is captured offline and synced when connectivity is restored.

3.20. UC-20 - Offline Attendance Capture
Actor: System
Goal: To detect when a worker leaves their assigned geofence and notify relevant parties.
Precondition: The worker is logged in and has an active attendance session.
Main Flow:
1.​ The system monitors the worker's location continuously.
2.​ The worker leaves the assigned geofence.
3.​ The system detects the breach.
4.​ The system logs the breach event.
5.​ The system sends a warning notification to the worker.
6.​ The system sends a breach alert to the Supervisor.
7.​ The system sends a breach alert to the Admin.
Alternative Flow:
1.​ If the worker returns to the geofence within the allowed grace period, the system
cancels the breach status.

Postcondition: The breach is logged; all relevant parties are notified.

3.21. UC-21 - Auto-Sync Offline Data
Actor: System
Goal: To automatically synchronize locally cached offline data when internet connectivity is
restored.
Precondition: The device was offline; attendance and proof data were cached locally.
Main Flow:
1.​ The device detects internet connectivity restored.
2.​ The system checks the local cache (SQLite) for unsynced data.
3.​ The system uploads attendance records.
4.​ The system uploads accomplishment proofs.
5.​ The system validates metadata for each submission.
6.​ The system updates the status to "Synced”.
7.​ The system notifies the user of successful sync.
8.​ If there are conflicts, the system alerts the Admin or Supervisor.
Alternative Flow:
1.​ If a sync conflict is detected (server record already exists), the system preserves the
existing server record and logs the conflict.
2.​ If the sync fails due to server error, the system retries after a delay.
Postcondition: All offline data is synced to the server; no data loss; sync status is updated.

3.22. UC-22 - Auto-Sync Offline Data
Actor: System
Goal: To automatically generate and send an alert when a Field Worker has 3 or more
consecutive absences.
Precondition: A Field Worker has 3 or more consecutive days of absence.
Main Flow:
1.​ The system detects the 3rd consecutive absence of a worker.
2.​ The system generates an alert.
3.​ The system adds the alert to the Admin's notification tab.
4.​ The system sends a notification to the Admin, Supervisor, and worker.
5.​ The Admin views the alert.
6.​ The Admin sends a warning notification to the worker.

Alternative Flow:
1.​ If the absence is due to an approved leave, the system does not count it as an absence.
Postcondition: All relevant parties are notified of the consecutive absence; the alert is
available for Admin action.

7. SYSTEM ARCHITECTURE
7.1. System Architecture
The proposed system employs a three-tiered client-server architecture that consists of
a Flutter presentation layer, a Supabase application layer, and a PostgreSQL + PostGIS data
layer. The presentation layer handles all user interface-related responsibilities such as user
authentication, input collection, and information display for the Admin, Field Supervisor, and
Field Worker user roles. The mobile application offers a mobile-first user experience to the
Field Worker while the web dashboard provides a unified view of the system to the Admin
and Field Supervisor. The application layer is primarily concerned with the execution of the
system’s core features, workflows, and business logic. It handles RESTful API request
handling and edge function execution among other responsibilities such as user verification
and validation. Lastly, the data layer stores and manages the system’s data, including user
profiles, face embeddings, geo-fencing polygons, attendance records, accomplishment proofs,
and leaves approvals data. The system uses TensorFlow Lite for on-device facial recognition,
Firebase Cloud Messaging for push notification handling, and the OpenStreetMap tile service
via the flutter_map package for map visualization. The architecture ensures modularity,
maintainability, and scalability while supporting the development of offline-first applications
and ensuring data and application-level security.

9. Data Requirements
9.1 Database Overview
​

The BantayGawaMobile database stores and manages all system data,

including user accounts, work areas, attendance records, accomplishment proofs,
leave requests, credit scores, notifications, alerts, and system logs. The database uses
PostgreSQL, a reliable relational database system, with additional support for
location-based data such as work area boundaries and GPS coordinates. Data is
organized into fifteen main tables that cover user management (Users, Roles,
Schedules), workforce operations (WorkAreas, WorkAreaAssignments, Attendance,
LocationTracking, Accomplishments, CreditBalance, CreditHistory), and workflow
management (LeaveRequests, Notifications, Alerts, WorkerReports, AuditLogs).
When workers are offline, their attendance and proof submissions are saved locally on
their mobile device using SQLite and automatically uploaded to the cloud database
once internet connectivity is restored. Images submitted as proof of work are stored
securely in the cloud with their metadata (date, time, location) extracted and saved in
the database for easy searching and reporting. The database uses security rules to
ensure that users can only access data they are authorized to view—workers see only
their own records, supervisors see records for their assigned areas, and the admin has
full access. This design ensures that the system remains reliable and accurate whether
workers are online or offline.

9.4 Database Normalization
​

The database for the BantayGawaMobile system has been designed and

normalized up to the Third Normal Form (3NF). Database normalization is a
systematic approach to organizing tables and columns to reduce data redundancy,
improve data integrity, and prevent insert, update, and delete anomalies.
The system adheres to the following normalization stages:
1.​ First Normal Form (1NF) - Elimination of Repeating Groups To satisfy 1NF,
every attribute in the database holds only atomic (indivisible) values, and each
record is unique. There are no repeating groups or arrays of data stored within a
single column.
●​ Application in the System: Instead of storing a comma-separated list of
assigned work areas directly inside the Users table, a dedicated junction
table (WorkAreaAssignments) was created. This ensures that every
assignment is a distinct, atomic record mapping one user to one work
area at a time.

2.​ Second Normal Form (2NF) - Elimination of Partial Dependencies To satisfy
2NF, the database must first be in 1NF, and all non-key attributes must be fully
functionally dependent on the primary key.

●​ Application in the System: The system inherently satisfies 2NF by
utilizing single-column, unique surrogate keys (UUIDs) such as user_id,
attendance_id, and workarea_id as the Primary Keys for every table.
Because composite primary keys are avoided, there are no partial
dependencies; every attribute in a table relies entirely on the single
primary key of that table.

3.​ Third Normal Form (3NF) - Elimination of Transitive Dependencies To satisfy
3NF, the database must be in 2NF, and there must be no transitive
dependencies. This means that a non-key attribute must not depend on another
non-key attribute; it must depend only on the primary key.
●​ Application

in the System: The system eliminates transitive

dependencies through proper table relationships and Foreign Keys. For
example, rather than storing a user's role name (e.g., "Field Supervisor")
and role description directly inside the Users table, which would create a
transitive dependency on the role_id, this data is separated into an
independent Roles table. The Users table only stores the role_id as a
Foreign Key. This ensures that if a role's description changes, it only
needs to be updated in one place, preventing data inconsistency.

9.6 Data Integrity Rules
​

The database enforces several integrity rules to ensure data accuracy,

consistency, and reliability. Every record has a unique ID to prevent duplicates and
ensure each record can be referenced correctly. When one table references another, the
database checks that the referenced record exists, preventing orphaned records. Fields
are restricted to specific values—for example, attendance actions can only be time-in,
break-in, break-out, or time-out, and status fields can only be active, inactive, or
pending. Critical fields such as user ID, timestamps, and GPS coordinates cannot be
left empty. Attendance logging is only allowed when the worker's GPS location is
inside their assigned work area, and facial recognition must match the registered face
before attendance is recorded. Records created offline are marked as "not synced"
until successfully uploaded to the cloud, preventing data loss or duplication. All
create, update, and delete actions are logged for accountability and review. Credit
scores are automatically updated based on attendance and approved accomplishments,
with no deductions for approved leaves, and point amounts are configurable by the
admin. These rules work together to keep the database clean, reliable, and trustworthy
across both online and offline operations.
9.7 Backup and Recovery Strategy
​

To ensure data integrity and guarantee business continuity in the event of

system failure or data corruption, the system employs an automated, routine backup
mechanism orchestrated through GitHub Actions. A scheduled CI/CD workflow (cron
job) is configured to execute on a weekly basis, automatically triggering a secure
extraction of the database schema and its records. Once the automated pipeline
generates the database dump, the backup artifact is securely archived, creating a
reliable, point-in-time snapshot of the system's data. By automating this process via
GitHub Actions, the system eliminates the risk of human error associated with manual
backups and ensures that a recent, stable version of the database is consistently
available. In a disaster recovery scenario, administrators can rapidly retrieve and
restore these automated backups, thereby minimizing potential downtime and
preventing catastrophic data loss.

10. Testing Strategy
10.1 Testing Overview
The testing strategy defines the structured approach for verifying and validating the
BantayGawaMobile before deployment. It ensures that the system satisfies its functional
requirements and non-functional quality attributes while identifying and resolving defects
throughout the development process.
The test shall conducted across the following levels:
●​ Unit Testing: Verifies the functionality of individual components and modules in
isolation, such as QR code authentication, attendance logging, facial recognition
validation, geofence validation, leave request processing, and accomplishment report
submission.
●​ Integration Testing: Verifies that different modules interact correctly with one
another. This includes validating the integration between QR code login and user
authentication, attendance logging with facial recognition and geofence validation,
accomplishment reports with proof image uploads, and report generation using
attendance records.
●​ System Testing: Verifies that the complete BantayGawaMobile system satisfies all
functional requirements and business rules specified in this Software Requirements
Specification. This includes validating role-based access for the Admin, Field
Supervisor, and Field Worker, attendance workflows, leave management,
accomplishment reporting, GIS workforce monitoring, and notification services.
●​ User Acceptance Testing (UAT): Conducted with representative users, including the
Admin, Field Supervisors, and Field Workers, to ensure that the system meets the
operational requirements of workforce attendance monitoring and field workforce
management.

Target Users
​

The primary users of Bantay-Gawa Mobile are the stakeholders directly involved in

workforce attendance monitoring and management within the Environment and Natural
Resources (ENRO), namely: Field Workers, who record their attendance through geofencing
and facial recognition, submit daily accomplishment reports, and receive work assignments
and notifications; Field Supervisors, who monitor field personnel, validate attendance
records, review accomplishment reports, assign tasks, and provide feedback; and the System
Administrator, who manages employee profiles, user accounts, work zone assignments, shift
schedules, attendance records, system configurations, and report generation. Each user is
assigned specific access privileges based on their responsibilities to ensure secure and
efficient system operations.

Major Functions
​

Bantay-Gawa Mobile provides the following major functions: (1) an Employee

Profile Management Module that maintains employee information, work zone assignments,
shift schedules, and user accounts; (2) a Geofencing-Based Attendance Module that restricts
attendance logging to authorized work locations using GPS coordinates; (3) a Real-Time
Facial Recognition Module that verifies the identity of employees during attendance
transactions to prevent proxy attendance; (4) a Mobile Attendance Module that records
time-in, time-out, GPS location, timestamps, selfie images, and device information; (5) a
Daily Accomplishment Reporting Module that enables field workers to submit completed
tasks, supporting photos, remarks, and work locations; (6) a Supervisor Validation Module
that allows supervisors to review attendance records, validate accomplishment reports, and
provide observations or feedback; (7) a Workforce Analytics Module that generates
attendance statistics, productivity reports, workforce utilization, and other analytical reports
to support management decision-making; (8) a GIS Workforce Monitoring Module that
displays employee locations, assigned work zones, attendance status, and completed
assignments on an interactive map; (9) a Notification Module that sends attendance
reminders, work assignments, schedule updates, and supervisor feedback; and (10) a User
and Access Management Module that implements role-based access control for
administrators, field supervisors, and field workers.

ASSUMPTIONS AND CONSTRAINTS
Assumptions
​

It is assumed that the field workers who will use the proposed Bantay-Gawa Mobile

system have access to personal Android smartphones (version 7.0 or higher) and possess the
basic digital literacy necessary to operate a mobile application. The researchers also assume
that although internet connectivity may occasionally be intermittent in some work locations,
the system's offline capabilities will help minimize disruptions during attendance recording. It
is assumed that GPS signals are available within designated work areas to support geofencing
validation and accurate location verification.
It is assumed that the Environment and Natural Resources (ENRO) has existing
Human Resource (HR) or administrative personnel who will serve as system administrators,

as well as designated field supervisors responsible for monitoring field workers and
validating attendance records. The researchers also assume that the ENRO can define
work-area geofences using available mapping data and will provide the necessary employee
information and other initial records required for system setup. It is also assumed that
employees are willing to use facial recognition as part of the attendance verification process
and that all users will comply with applicable privacy and data protection policies governing
the collection and processing of attendance information.

Constraints
​

The development and implementation of Bantay-Gawa Mobile are subject to several

limitations. The proposed system must be developed within the available budget of the Local
Government Unit (LGU), making the use of open-source and cost-effective technologies
necessary. The mobile application is intended to support Android devices running version 7.0
or higher; therefore, older devices may not fully support certain features, particularly facial
recognition. Since field personnel may work in areas with unstable internet connectivity, the
system is designed to allow offline recording of core attendance functions, with
synchronization occurring once a stable connection becomes available. In addition, the
system must comply with the LGU's data retention and privacy policies, particularly in
handling attendance records, GPS locations, and biometric information. To enhance data
security, facial recognition data and other sensitive biometric information will be securely
stored and managed in accordance with applicable privacy and data protection regulations.
